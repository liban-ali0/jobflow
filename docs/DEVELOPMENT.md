# Developing Offerbound

How the code is put together, the commands, and the gotchas. For installing and using Offerbound, see the README.

Offerbound: a job application workflow where Claude Code or Codex does the work and a local Next.js app controls and tracks it. `AGENTS.md` (imported by `CLAUDE.md`) holds the rules for engines running workflow steps; this file is for developing the code. `PLAN.md` has the agreed plan and phase status.

## Commands

Run from the project folder (Node 22.13+, Windows primary but must stay portable):

| Task | Command |
|---|---|
| First setup | `npm run setup` |
| App for daily use (production build in `web/.next-prod`, rebuilt only when sources change, always 127.0.0.1) | `npm start` (`scripts/start.mjs`) |
| App in the background, as a Windows app (supervisor restarts `start.mjs` on crash; `data/service.json`, log in `data/logs/`; sign-in start per copy: Windows HKCU Run entry running `data/autostart.vbs`, macOS LaunchAgent, Linux XDG autostart `.desktop`; all off until `autostart on`) | `node scripts/service.mjs start\|stop\|restart\|status\|update\|logs\|autostart on\|off` |
| App (dev, http://localhost:3000) | `npm run app` |
| Type check | `npx tsc --noEmit` (in `web/`) |
| Lint | `npm run lint --prefix web` |
| LinkedIn collector | `npm run find` (or `node scripts/collect.mjs --dry-run`) |
| Data CLI | `node scripts/jobs.mjs help` |

There is no test suite. Verify changes with type check + lint, then drive the running app with Playwright (`playwright` is a root dependency; setup installs its Chromium, which the app also uses for PDFs) and look at screenshots. The user uses the app live: before any test that saves (settings, statuses, questions, conversations), snapshot the affected rows and restore them afterwards; prefer checks that only change the URL or set `data-theme` in the test browser.

`web/` is Next.js 16 with breaking changes: read the relevant guide in `web/node_modules/next/dist/docs/` before writing Next code (see `web/AGENTS.md`). The `react-hooks/purity` lint rule rejects `Date.now()` in components; put time-based logic in `src/lib`.

## Architecture

**Engines run steps; the app starts them.** `web/src/lib/engine.ts` spawns either `claude -p --output-format stream-json --permission-mode dontAsk` (prompt `/<skill> <arg>` on stdin) or `codex exec --json` (the skill's SKILL.md body sent as the prompt, sandbox `workspace-write`). Steps are `.claude/skills/<step>/SKILL.md`, shared by both engines; the engine/model/effort per step comes from Settings. Script stages (`find-jobs` → `scripts/collect.mjs`) run Node directly. Each run is a row in `runs` with streamed `progress` lines; Assistant conversations reuse the engine session (`--resume` / `codex exec resume`).

**Headless permissions are the project's `.claude/settings.json` allow list** (Bash and PowerShell forms of `node scripts/jobs.mjs …`, web tools, edits under `candidate/` and `jobs/`). Commands with `cd`, pipes, or `&&` are refused, which is why AGENTS.md demands plain commands. Both `claude` and `codex` must have trusted the folder or runs fail (handled with explicit messages in `engine.ts`).

**One data layer, two callers.** `web/src/core/db.mjs` is plain ESM on `node:sqlite` (types in `db.d.mts`) so `scripts/jobs.mjs` can run it without a build; the app wraps it in `src/lib/data.ts`. Schema changes go in `SCHEMA` plus `ADDED_COLUMNS` (migration for existing databases). Settings = `config/defaults.json` overridden per top-level key by the `settings` table.

**Ranking:** the `rank-jobs` skill judges each job and writes an assessment file; `node scripts/jobs.mjs score` turns it into a score via `src/core/score.mjs` (role/country/freshness computed from settings, legitimacy < 4 excludes). Accepts `N` or `ids:1,2`.

**User facts and questions:** `candidate/facts.md` overrides the CV and feeds `build-profile`; engines ask the user through `jobs.mjs ask`, and answers are written back to `facts.md` (or the job's notes) by `answerQuestion` in `data.ts`. Extra ranking rules live in settings `customRules`.

**Today screen state lives in the URL.** `src/lib/departures.ts` builds the board list from query params (view, filters in `filters.ts`, sort via `tableSort` in `sort.ts` with separate params per table, pagination) and is shared with the `/export` CSV route so exports match the screen.

**Theme:** `src/lib/theme.ts` derives brand CSS variables from Settings (primary, secondary, mode) for light and dark, adjusting text colours to keep WCAG AA; neutral light/dark tokens are in `globals.css`. Tailwind token names are historical: `saffron` = secondary, `teal` = link, `ink` = body text, `signal` = secondary as text on tables, `board-*` = job tables (light in light mode), `chrome-*` = the always-dark workflow strip.

**Job sources:** three routes, all without bypassing bot protection (no fingerprint spoofing, stealth plugins, proxies or VPN tricks: the user ruled that out).
1. `scripts/collect.mjs` (find-jobs) fetches LinkedIn's public guest feed and Workable's public job search API. Countries are searched in priority order, and descriptions are fetched only after all list pages, so the per-source request budget never cuts off a lower-priority country.
2. `browse-jobs` (Claude Code only, run with `--chrome`, starts after find-jobs when a Chrome source is on) reads Indeed, Bayt, GulfTalent, Naukrigulf and Kariyer.net in the user's own Chrome through Claude in Chrome. `.claude/settings.json` allows `mcp__claude-in-chrome`. The extension must be allowed on each site (for example `ae.indeed.com`).
3. The Offerbound browser extension (`extension/`, load unpacked) works with any engine: it posts the open page to `/api/capture` (extension origin plus the key from Settings → Sources, `lib/capture.ts`), and `import-jobs` picks out the jobs.

Sources come from `config/defaults.json`; only the on/off choice is saved (`normalizeSources` in `db.mjs`).

**Shared with friends (route A):** each person runs their own copy with their own Claude subscription. Nothing user-specific belongs in code, skills, or `config/defaults.json` (which ships with no countries or roles); the user's choices live in their database and `candidate/`. New users go through `/setup` (engine check via `checkEngine` in `engine.ts`, CV upload, facts, targets, build-profile). Roles are user-defined (`key` from the label), so code and skills must not assume software/AI/IT; base CVs are `candidate/base-cv-<role key>.md`.

**Schedule:** `src/instrumentation.ts` starts a one-minute clock that POSTs `/api/schedule` with a per-process key; `lib/scheduler.ts` decides from the runs table (so it survives restarts): fast-track `find-jobs` (trigger `schedule`) every N minutes within the active hours, then `rank-jobs ids:` for the new fast-track jobs; the daily run (trigger `daily`) at the set time: find-jobs, browse-jobs if a Chrome source is on, then rank-jobs. Manual find-jobs still chains browse-jobs itself. Restart the app after changing `instrumentation.ts`.

**Runs and statuses:** `closeAbandonedRuns` (first launch after start) fails engine runs left running, but leaves the extension's runs (`engine: "extension"`) alone for 30 min; `/api/collect/plan` and `/api/listings/browser` refuse while a fresh run is going and close a stale one. `jobs.mjs score` changes status only for found/ranked/excluded jobs (a selected or sent job keeps its stage); `saveDocument` of a package document puts a `ready` job back to `researched`. `setStatus` routes outcomes through `recordOutcome`. Board stage `due` = reminder passed (Today shows the first 8 of `followUpsDue`).

**Password (optional, off by default):** `core/password.mjs` keeps a scrypt hash and a session-signing secret in `data/password.json` (0600); no file = no login. `proxy.ts` runs `signInGate` (`lib/login.ts`) after the device checks, for localhost too: open are `/_next/`, icons, the manifest, `POST /api/login|logout`, `/api/schedule` (tick key) and the extension routes when they carry `x-jobflow-token` (they check it with `extensionDenied`); any `next-action` request needs a session whatever its path. The sign-in page is plain HTML from the proxy (outside the app layout, so nothing leaks). Cookie `offerbound_session` = expiry.nonce.HMAC (12 h, or 30 days with "keep me signed in"); a new password or "Sign out other devices" rotates the secret. Wrong tries: after 5 in a row, waits up to 60 s (in memory). Settings actions `savePassword`/`removePassword` need the current password. Forgotten: `node scripts/password.mjs off` (not in the engines' allow list, and engines cannot edit `data/`).

**Sharing:** friends install with `npm run setup` + `npm start` (README). `next.config.ts` sets `turbopack.root` to the web folder (a fresh clone has two lockfiles and otherwise fails to build). Never let the server listen beyond 127.0.0.1: `proxy.ts` trusts a localhost Host header. `jobs.mjs cv-text` (scripts/cv-text.mjs, pdfjs-dist) gives any engine the CV text; build-profile uses it. Tested from a fresh clone: setup, build, all pages with empty data.

**Story bank and debriefs:** `candidate/stories.json` (`core/stories.mjs`): stories need a situation, an action, a result and skills; `jobs.mjs story [<id>] --file` adds them and flags figures the profile and facts do not back (`checkFacts`), and the user confirms or removes each one on Profile (`components/story-bank.tsx`). `jobs.mjs stories --job <id>` returns `matchStories` against `core/requirements.mjs` `jobRequirements` (report.json requirements, else research's ATS keywords), worked out in code. At the interview stage the job page shows the Interview panel (`components/interview-prep.tsx`, `app/interview-actions.ts`): matched stories, "Practise with the Assistant" (a conversation that follows `.claude/skills/interview-practice/SKILL.md`), and notes after the interview → stage `interview-debrief` (writes `debrief.md` and `thank-you.md`, document types `debrief` and `thank_you`; an earlier round's files are renamed `debrief-round-<n>.md` first). The thank-you note opens in Gmail like a follow-up (`composeFor(id, "thank_you")`); with the extension (0.6.1) Send records a "thank-you sent" event. After career-ops' story bank, interview plan, practice, debrief and red-flag modes (MIT).

**Interview pack:** `interview-pack` skill, started when the user marks a job "Interview" (`recordOutcome`) or from the outcome bar.

**Extension (main route for applying):** `extension/` is MV3 for Chrome, Edge and Firefox (`background.service_worker` for Chrome, `background.scripts` for Firefox; `common.js` is shared). `bridge.js` runs on the app's localhost pages: the app talks to it with `window.postMessage`; `background.js` accepts a page's request only when the browser's own `sender.origin` matches the origin the page claims and (except `connect`/`ping`) the connected address (`fromOfferbound`); the first connect is confirmed in `connect.html` with a nonce. The apply tab is filled only while it is on the form's origin or a known ATS host (`ATS_HOSTS`, `formOrigin` in the tab state), top frame and same-site/ATS frames only (`components/use-extension.ts`: ping, connect, apply), and Connect in Settings → Sources hands over the address and key. `background.js` opens each ready job's form (Workable/Lever apply addresses, LinkedIn refused), injects `fill.js` + `apply.js` into every frame on each load, and keeps per-tab state in `storage.session`. `apply.js` refills new steps, reports what is left (`POST /api/apply/[id]/state` → `jobs.apply_state` "waiting" + `apply_missing`), shows the bar, and detects the user's submit (confirmation text or URL, or the form gone without errors) → `POST /api/apply/[id]/applied` (writes `application.md`); typed answers can be saved with `POST /api/facts` (`appendFact`). Extension routes are checked by `extensionDenied` (no website origin, plus the key). Test with Playwright (`channel: "chromium"`, `--load-extension`) and Firefox via puppeteer-core `installExtension`, on `web/public/demo/apply/full.html`; restore `candidate/facts.md` afterwards.

**Email (Gmail through the extension):** no password or OAuth. `background.js` checks Gmail's feed of unread inbox mail (`https://mail.google.com/mail/u/<account>/feed/atom`, the browser's own session) on a 15-minute `chrome.alarms` timer and on "Check Gmail now", and posts entries to `/api/mail`. `lib/mail.ts` sorts each one (`classifyMail`: noise, rejected, offer, interview, action, received, replied; EN/TR/AR phrases folded like `fold`, after career-ops' reply-watch, MIT) and matches it to a sent application (`matchMail`: contact email domain, company domain, company name, title words). Kept in the `mails` table (state new/done/dismissed; unrelated mail only as its id, 'ignored'); nothing changes until the user confirms (`app/mail-actions.ts`). Sending: `composeFor` builds Gmail compose URLs (follow-up document, email application); with the extension, `compose-watch.js` in that tab notices Send (button or Ctrl+Enter, then Gmail's "Message sent" or the tab leaving compose) and `/api/mail/sent` records it. Settings → Email: `email.watchReplies`, `email.account`; last check in settings `mailCheck`. Test with Playwright: route `mail.google.com` and launch with `--host-resolver-rules=MAP *.google.com ~NOTFOUND` so a test never reaches Google (tabs the extension opens load before routes attach).

**Is the listing still open:** `core/liveness.mjs` (`checkListing`) answers open/closed/unsure with a readable reason: LinkedIn's guest job page (closed banner vs. apply control; the "sign in to apply" control stays on closed listings, so it counts only without the banner), Workable's job APIs (404 = gone), otherwise the page through career-ops' vendored `classifyLiveness` plus Turkish/Arabic closure notices. Indeed refuses the server (`listingSite` → null; `browserListing` true): the extension checks it in the user's browser (`checkListings` in background.js, minimized window, `jobflowReadPage` in collect.js, stops at a robot/captcha page, alarm every 6 h and with Today's Check listings) through `/api/listings/browser` (GET plan of up to 20 due, starts run `browser-listings`; POST one page → `classifyBrowserPage`; `/done` finishes the run). Test with Playwright: route `*.indeed.com` and map it to ~NOTFOUND. A wrong "closed" costs a real job, so anything unclear is "unsure". Listing links come from captured pages and engines, so `load` uses node:http/https with `guardedLookup`, which checks the address at connect time (no DNS rebinding gap): `publicAddress` blocks private/reserved IPv4 (BlockList) and allows IPv6 only in 2000::/3 minus 6to4/Teredo/documentation; written-out IP hosts are checked in `checkedUrl` (Node skips lookup for them); ports 80/443, no credentials; redirects followed by hand through the same checks; one 20 s deadline for the whole check including redirects (the socket `timeout` option is only idle time, so a drip-feeding server would never end), decompressed body capped at 3 MB with a settle-once guard. Do not switch it back to global fetch. `scripts/check-open.mjs` (stage `check-open`, daily after rank-jobs, honours `JOBFLOW_ROOT`) stores `jobs.listing_state/_reason/_checked_at` via `setListing` (no `updated_at` change); a site that answers 429/403/bot wall is skipped for the rest of the run and nothing is stored. "kept" = the user said it is open; never rechecked. Statuses never change on their own: Today's "Listings that closed" and the job page offer `setAsideClosed` (→ Excluded, reason "The listing closed").

**Reposts:** `addJob` treats the same title + company + country + site (`siteOf`) within 30 days as the same opening (another country is another opening); a new link on a later day (20 h+) bumps `jobs.relisted_count/relisted_at`, refreshes `posted_at`, and adds a "relisted" event instead of a new row. Older ones (30–90 days) are separate rows linked by `core/reposts.mjs` `findReposts` (career-ops detect-reposts rules, MIT: company without legal suffix, same SET of title words, same site host, found ≥1 and ≤90 days apart). `lib/reposts.ts` `repostNote` → "Applied before" / "Set aside before" / "Listed again" (after applying: probably still open) / "Reposted", on the job page and as a board chip; `jobs.mjs get` returns `otherListings` for rank-jobs.

**CV fact check:** `core/fact-check.mjs` runs career-ops' vendored `verify-cv-facts.mjs` (path-resolver import stubbed; self-test 136/136) on the tailored CV, cover letter and email against `candidate/profile.md`, `facts.md`, `base-cv-*.md`; plus Offerbound's negation rule ("I have not worked with X" is not a claim). "This is true" writes `candidate/cv-facts.json` (career-ops' allow lists). Shown per document tab (`FactPanel`); `jobs.mjs factcheck <id>` is run by tailor-job and improve-cv to fix unbacked claims.

**Follow-up timing:** `lib/followups.ts` `CADENCE` (after career-ops' followup-cadence, MIT): `follow_up_due` is the one reminder date for applied (first after Settings `followUpDays`, at most 2 follow-ups, then kind "quiet"), replied (check-in after 3 days), and interview (thank-you 3 h after `interview_at`, then a check-in after 5 days; "thank-you sent" event). `followUpsDue()` returns a `kind` per job; Today's "Waiting on you" renders `FollowUpRow` by kind. The follow-up skill writes a shorter second one and never a third.

**Patterns:** `lib/patterns.ts` `findPatterns` (after career-ops' analyze-patterns and rejection-latency, MIT) shows on Statistics: best/worst group by role, country, source, work mode, score band, apply speed, email vs form (≥3 decided per group, ≥5 decided overall), a score floor, median days to reply/rejection, interviews silent 30+ days, and repeated "Not interested" reasons with "Add as a ranking rule" (`addRankingRule`).

**Archive and the Jobs page:** `jobs.archived_at` (separate from status, never deletes). `archiveStale` (every 30 min from `/api/schedule`) archives found/ranked/excluded jobs whose `COALESCE(posted_at, found_at)` is older than Settings `freshness.archiveAfterDays` (default 7, 0 = off); `archiveJobs` lets the user archive any job not yet applied to (`ARCHIVABLE`); a status change other than to excluded clears `archived_at`. Lists pass `archived: false` (Today, Board, cap counts, `countByStatus`, `jobs.mjs list` unless `--archived`). `/jobs` (app/jobs/page.tsx) has one table per stage (Not ranked, Ranked, Selected, Preparing, Excluded, Archived) with `BulkSelection mode` choosing the bulk actions.

**Applying:** `lib/apply.ts` builds a job's application pack (details from the tailored CV header, `answers.md` as question/answer with "For you, not the form" notes split off and open answers filled from answered questions in `facts.md`, PDFs, the email application when a contact email is confirmed). Three ways, never submitting: `apply-job` (Claude Code, `--chrome`, fills the form in the user's Chrome and stops before Submit; refuses LinkedIn), the extension's "Fill this form" (`extension/fill.js`, label heuristics, React-safe value setting, never ticks consent; `/api/apply*` with the extension key), and an `.eml` draft (`/api/jobs/[id]/email-draft`). Demo forms for testing live in `web/public/demo/apply/` (they record any submit in `window.__submitted`); never test on a real application. Claude in Chrome cannot open localhost, so the apply-job step is tested on the demo forms with the Playwright MCP tools instead.

**ATS score:** `web/src/lib/ats.ts` combines three deterministic parts by `WEIGHTS` (35/35/30 with a keyword list, 60/40 without): the vendored ATS Screener engine (`web/src/vendor/ats-screener`, MIT, six simulated ATS platforms; see its README before updating it; its verb list and number patterns are exported), Offerbound's phrase-level match against research's "ATS keywords" list, and the VeriWorkly review (`@veriworkly/ats-engine`, npm, MIT, pinned 0.7.0: readiness rubric with evidence and fixes, the listing's requirements met or missing, what an ATS parses). Its rules that duplicate Offerbound's checks are merged (`COVERED`, `SAME_CHECK`). Template layout is checked separately by career-ops' `verify-ats.mjs` (`web/src/vendor/career-ops`, MIT, one regex patched and marked) in `lib/template-check.ts`, server-only, kept out of the score. Keep it deterministic: no AI in the score.

Gotchas: `next dev` does not hot-reload changes to `web/src/core/*.mjs`, so restart the app after editing them. Turbopack can also keep serving cached CSS without Tailwind classes from new or edited files (even across restarts); if a new class has no effect, change `globals.css` (and change it back) to force a rebuild. Client components must not import `core/db.mjs` (it pulls in `node:sqlite`); shared constants go in import-free modules like `core/levels.mjs`. `node:sqlite` rows have a null prototype: copy them (`{ ...row }`) before passing them to a client component. Offerbound is for any field and level: experience levels, max years (null = no limit), and title words to skip are settings, read through `normalizeExperience` in `db.mjs`.

`candidate/`, `jobs/`, and `data/` hold personal data and are git-ignored.
